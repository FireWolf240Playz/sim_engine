# Task 3.5 — real traffic shapes (engine, presets, CLI)

> Roadmap 3.5, first of two cards (3.5 engine → 3.5b web picker).
> Independent of 3.1–3.4: it can be built at any point in the wave.

## Goal
`TrafficPattern.shape` bends the base rate over the traffic window (`flat`,
`ramp`, `diurnal`, `black_friday`), arrivals follow that curve exactly, the
run-size limit counts it, and the CLI runs a named day with `--traffic`.

## Measured first (2026-11-15, throwaway implementation, 3 seeds each)
`microservice_platform` (20 nodes), no incident, 120 s, quiet rate 4 rps:

| shape | requests | resilience | failed |
|---|---|---|---|
| flat | 395–479 | 49.8 – 66.0 | 11–52 |
| ramp | 902–931 | 34.5 – 38.0 | 236–259 |
| diurnal | 941–997 | 21.9 – 31.1 | 278–354 |
| black_friday | 1251–1333 | 23.8 – 24.5 | 438–484 |

`production_platform` (15 nodes) at 4 rps: flat 89.9–92.4, black_friday
54.0–59.9. So "Black Friday breaks it harder than a flat day" holds with a
wide margin, and the test pins it on two seeds. (At 1–2 rps the 15-node
example absorbs Black Friday: a shape is not a guaranteed failure.)

The sampler below delivered each fifth of every curve within 6% of its
integral over 60 seeds, and the closed-form `expected_requests` matched a
brute-force integral within 0.2%.

## Decided, and why
- **`base_rps` is always the quiet rate; `shape_peak` says how many times
  busier the peak is.** One rule for every shape, and a flat config means
  what it always meant. Defaults: 3 for `ramp` and `diurnal`, 5 for `black_friday`.
- **The curve is laid over the traffic window**, by the fraction `u` of the
  window elapsed, so a shape means the same on a 60 s run and a 600 s run.
- **Thinning, not inversion.** The existing sampler inverts each rate law
  exactly; `sin²` has no closed-form inverse. Thinning (draw candidates at
  the peak rate, keep each with probability `rate / peak`) is exact for any
  bounded curve and is six lines. Flat patterns do not go through it: they
  draw exactly what they always drew, and every pinned score rests on that.
- **A shape and exponential growth together are refused**: two rate laws.
  A spike still overrides the curve while it lasts, as it does today.

## Design (decided)

### The curves
With `u = (t - start_time) / duration` and `P` the peak, the rate is `base_rps` times:

```
flat          1
ramp          1 + (P - 1) u
diurnal       1 + (P - 1) sin²(π u)
black_friday  1                          u < 0.4
              1 + (P - 1)(u - 0.4)/0.1   0.4 ≤ u < 0.5
              P                          0.5 ≤ u < 0.8
              P - (P - 1)(u - 0.8)/0.2   0.8 ≤ u
```

The same formulas are mirrored in the web (3.5b) and pinned there with the same numbers.

### `TrafficPattern`
- `shape: "flat" | "ramp" | "diurnal" | "black_friday" = "flat"`;
  `shape_peak: float | None` (> 1). `DEFAULT_SHAPE_PEAK = {"ramp": 3.0, "diurnal": 3.0, "black_friday": 5.0}`.
- Validation (the model is strict, an ignored field is an error): `shape_peak`
  on a flat pattern is refused (message names `shape_peak`); a shape with
  `pattern_type: exponential` is refused (message says `exponential`).
- `rate_at(t) -> float`, public and pure: 0 before the window and from its
  end on; the spike rate while a spike is active; else the exponential law or
  `base_rps ×` the curve. `traffic.py::_target_rps` becomes a call to it.
- `expected_requests(horizon)`: the shape's integral in closed form inside
  `_base_requests(a, b)` (the spike arithmetic around it already subtracts the
  base over the spike window, so it keeps working). The integrals of the multiplier from 0 to `u`:
  ramp `u + (P−1)u²/2`; diurnal `u + (P−1)(u/2 − sin(2πu)/(4π))`;
  black_friday piecewise: `u`; `u + (P−1)(u−0.4)²/0.2`;
  `0.5 + 0.05(P−1) + P(u−0.5)`; that at 0.8 `+ P(u−0.8) − (P−1)(u−0.8)²/0.4`.
  Multiply by `base_rps × duration`.
- `peak_rps(horizon)`: the largest multiplier reached by the horizon (`P`
  once `u ≥ 0.5` for diurnal and black_friday; the curve's value at the
  horizon before that, and always for ramp), times `base_rps`, then the spike as today.
- The run-size limit and the API budget read these two methods, so they
  count the shape with no further change (pinned: 1,000 rps × 400 s is
  refused on Black Friday as "about 1,120,000 requests, peaking at 5,000 rps").

### The sampler (`generate_traffic`)
For a shaped pattern, outside a spike:
```python
ceiling = pattern.base_rps * peak            # the curve never exceeds it
gap = rng.exponential(1.0 / ceiling)
if now + gap >= boundary: jump to the boundary, continue      # as today
yield env.timeout(gap)
if rng.random() * ceiling >= pattern.rate_at(env.now): continue   # thinned
emit the request
```
Flat (and exponential) patterns keep today's path untouched. Spike edges
stay breakpoints; inside the spike the constant-rate path applies.

### Presets and the CLI
- `TRAFFIC_PRESETS` with `black_friday` (shape `black_friday`, peak 5) and
  `eu_business_hours` (shape `diurnal`, peak 3);
  `traffic_preset(name, base_rps, duration) -> TrafficPattern`; an unknown
  name raises `KeyError` listing the names.
- `run` and `demo` gain `--traffic NAME` (`choices` = the preset names): the
  config's traffic is replaced by the preset at the config's own `base_rps`
  and traffic `duration` (and `start_time`), and the config is validated
  again so the run-size limit applies. Print one line saying which day runs.
  (These two tests were written without a prototype; the rest of the file ran green against one.)

## Constraints
- A flat pattern's arrival times do not move by one bit.
- Pydantic holds the configuration; the sampler holds no state beyond the RNG.
- Full type hints. No new dependency.

## Out of scope
- The web picker (3.5b). Weekly seasonality, a user-drawn curve, more than one peak, shapes in the importers.
