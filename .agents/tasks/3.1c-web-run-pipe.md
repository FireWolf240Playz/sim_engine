# Task 3.1c — the web runs through the stream

> Roadmap 3.1, third of three cards. Needs 3.1b (`POST /runs`, the event stream).

## Goal
Pressing Run starts a run with `POST /runs` and reads its stream: the verdict
appears when `measured` arrives, the Fix-it plan fills in when `result`
arrives, and the page holds the run's ticks, chaos windows and feed lines
for the live view (3.2).

## Measured first (2026-11-15)
On the 20-node example the stream delivers `measured` at 0.7 s and `result`
at 27 s (see 3.1b). With `/simulate` the page shows "Running…" for all 27 s,
and past 60 s (`TIMEOUT_MS.run`) it gives up. A 5-seed run on that example
plans five times and cannot finish inside that deadline at all.

## Design (decided)

### `lib/runStream.ts` (pure)
`RunFeed` is `{phase, started, ticks, chaos, lines, seedsDone, measured, typicalSeed, result, error}`,
`phase` one of `idle | running | measured | done | failed`.
- `parseRunEvent(name, data)` → typed event, or `null` for `ping`, an unknown name, or a body that is not JSON.
- `reduceRun(feed, event)` → a new feed. `started` starts over from
  `EMPTY_FEED`. After `done` or `failed` it returns the same object. It
  replaces only the array the event touches: a tick leaves `lines` and
  `chaos` identical (`===`), so a panel that only shows lines is not redrawn
  per tick.
- `provisionalResult(feed)` → `null` before `measured`; then a
  `SimulateResponse` built from the stream (`summary` = measured, `chaos` =
  `started.chaos`, `timeseries` = the ticks, `report_png_b64: null`, plus
  `seeds` / `typical_seed` when the run has them); once `result` arrived,
  that object itself.
- `planPending(feed)` → `phase === "measured"`.

### `api/runStream.ts`
`watchRun(url, {onEvent, onFail}, open = (u) => new EventSource(u))` returns
a stop function. It listens for each `RUN_EVENT_NAMES` entry and `ping`,
hands on every parsed event, and closes the source after `result` or `error`
(the browser would otherwise reconnect to a finished stream). Failure rules:
- `onerror` with `readyState` 0: the browser is reconnecting (it sends
  `Last-Event-ID`, the engine resumes). Do nothing.
- `onerror` with `readyState` 2: `onFail("the stream from the engine closed before the run finished")`, once.
- nothing at all, not even a ping, for `SILENCE_MS` (45 000; the engine pings every 15 s): close, `onFail("the engine stopped answering")`.
- after the end, or after stop: no event, no failure, no timer.

### `RunStateContext`
- A run is `api.startRun(body)` then `watchRun(api.runEventsUrl(run_id), …)`.
  `body` is `{config, playbook}` plus `n_seeds` in confidence mode.
- Keep the token guard, and now also **stop the previous stream** when a new run starts.
- `feed` (new context field) is folded with `reduceRun` on every event.
- `result` changes only twice per run, never per tick: on `measured`
  (`provisionalResult`) and on `result`, both through `shareResult`. Until
  `measured`, the previous result stays on screen, dimmed, as today.
- `isPending` is true from Run until `measured` (or a failure). `planPending`
  (new field) is true from `measured` until `result`. Run and the incident
  picker are usable again as soon as `isPending` is false.
- `measuredRun` / `measuredNodes` are set on `measured`. An apply's change-log
  record completes on `measured` too (`completeRecord` reads the score and the
  findings, both final there).
- 5-seed mode: `seedsDone` of `started.seeds.length` is known while running;
  the Run button reads `Running… 3/5`.
- Failures. The POST is refused, or an `error` event / `onFail` arrives
  before `measured`: today's failure path, but first ask
  `api.runStatus(run_id)` once and use its `result` if the run is in fact
  `done`. After `measured` (the plan failed or the stream died): keep the
  measured result, clear `planPending`, and say in the Fix-it panel
  `The fix could not be verified: <message>`. That is not a page-level error.
- `api.simulate` stays in the client; the simulator page no longer calls it.

### What is provisional while `planPending`
The summary at `measured` has no `suggestions`, no `fix_outcome`, no
`verified_status`, and its `cost_grade` is graded on unverified labels (the
engine re-grades once the plan exists). So, until `result`:
- Fix it panel: one line, `Verifying the fix by simulation…` (`fixPanelView`
  gets an optional `planPending` input and a `"verifying"` note; existing
  inputs behave as before, `rerun.test.ts` is locked).
- Cost grade tile and the Sizing table's status column: dimmed, `title="verifying…"`.
  Resilience, SLA, P95, failed requests and the findings are final at `measured`; do not dim them.
- "Apply & re-run" is unavailable; Export stays available (it re-runs server-side).

## Constraints
- The engine call still lives in `RunStateContext` exactly once.
- No new dependency (`EventSource` is the browser's). No `memo` added.
- `src/core/lib` stays helpers only; tests live in `web/tests/`.

## Out of scope
- Drawing the ticks or the feed (3.2). `custom_chaos` (3.3). Cancelling a run.

### Notes for review
- **Run again doubles the wait.** The abandoned run's plan keeps computing on the server (2 worker threads), so the new run's plan took 41 s instead of ~21 s. Cancelling a run was out of scope; a cancel endpoint, called when the client stops a stream, would fix it.
- **The diagram's sizing words are unverified while the plan runs.** During those ~20 s every node on the 20-node example read `OVERSIZED` (the unverified label); the verified labels land with `result`. The card only dims the grade tile and the sizing table. The live view (3.2) shows live load during playback, which covers most of that window; after it, the words may still change once.
