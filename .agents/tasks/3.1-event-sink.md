# Task 3.1 — the engine can be watched: event sink, full ticks, the feed

> Roadmap 3.1, first of three cards (3.1 engine → 3.1b API → 3.1c web).
> Every other Wave 3 card builds on the tick and the events defined here.

## Goal
A caller can hand `CloudSimulator` a sink and receive, as the run happens, a
tick that says what happened in it and every chaos window as it opens and
closes; `sim_core/feed.py` turns those events into the lines a person reads;
and the Fix-it plan can be attached after the summary instead of inside `run()`.

## Measured first (2026-11-15, seed 42)
- **The simulation is not the wait.** The roadmap says "one 20s blocking
  request". The run itself takes 0.02 s (6 nodes) to 0.10 s (20 nodes) for
  120 simulated seconds; the Fix-it plan after it takes 0.4–0.7 s on the
  6-node examples, 6–12 s on `production_platform`, 24–37 s on
  `microservice_platform`. So `run()` is split (`attach_fix_plan`), and the
  stream in 3.1b sends the verdict before the plan.
- **60 ticks arrive in under 0.1 s.** Nothing can be "watched" at engine
  speed; the web plays the ticks back against its own clock (3.2). The engine
  only has to make each tick complete.
- **A tick lacked what a viewer needs:** no request counts, no live capacity
  (an outage was invisible), no retries, no per-edge traffic; a random chaos
  victim was named nowhere.
- **Building the tick at sample time changes no existing number:** a
  throwaway implementation gave tick-for-tick identical `timeseries()` and
  identical summaries on the 4 examples × {clean, `db_failover`,
  `dependency_timeout_cascade`}, and the 426 existing tests stayed green.

## Design (decided)

### 1. The sink
`CloudSimulator(config, event_sink: Callable[[dict[str, Any]], None] | None = None)`.
Called synchronously, in simulated-time order. Two event types:

```python
{"type": "tick", **tick}                      # one per sample, see 2
{"type": "chaos", "t": 5.0, "phase": "start" | "end",
 "event_type": "component_failure", "node": "db" | None, "intensity": 0.5}
```

The sink observes. It draws no random number and schedules nothing, so a
watched run and an unwatched run of the same seed give the same summary
(pinned). With no sink, no event dict is built. Every event is plain JSON
(`float(env.now)`, `event_type.value`, ints that are `int`, never a numpy scalar).

### 2. The tick (also what `timeseries()` returns)
Built once, in `MetricsCollector.sample_utilization(env_now) -> dict[str, Any]`,
kept in a list, and returned; `timeseries()` returns copies of that list, and
the engine sends the same content to the sink. One source, so the stream and
the finished run cannot disagree.

```python
{
  "time": 4.0,
  "p50_latency": 1.8, "p95_latency": 3.1, "sla_met": 0.9,      # unchanged; None when no request ended in the window
  "arrived": 9, "completed": 7, "failed": 1,                   # new: in the window that ends at this tick
  "per_component": {"db": {
      "utilization": 0.7, "queue_length": 2.0,                 # unchanged
      "capacity": 2, "in_use": 2, "retries": 0}},              # new: live slots now; retries in the window
  "edge_flow": [9, 9, 4],                                      # new: requests that set off along config.topology.edges[i]
}
```

- The window is "records appended since the previous sample" (a cursor into
  `self.requests`), replacing the end-time scan `timeseries()` does today.
  The two differ only if a request ends at exactly a tick's timestamp and
  SimPy runs the sampler first; times are continuous draws, and the 12 runs
  above were identical.
- `arrived`: `record_arrival` counts; the tick takes the difference.
- `retries`: difference of `retry_counts[name]` since the previous tick.
- `edge_flow`: `MetricsCollector(..., edge_count=len(config.topology.edges))`
  and `record_edge(index)`, called in `_walk` right before it recurses into
  `edge.target` (the request sets off). Map edge → index once in the engine.
- Hand the sink (and `timeseries()` callers) a copy, never the stored dict.
- `UtilizationSample` and `collector.utilization` stay as they are (tests read them).
- Ticks stop at the last sample (118 s of a 120 s run), as today. Leave it.

### 3. Chaos, as it happens
`inject(env, topology, event, rng, notify=None)`; each handler calls
`notify("start", node)` right after it applies and `notify("end", node)`
right after it releases. `node` is the victim's name (`component_failure`:
the drawn victim when there is no target; `cache_outage`: the cache hit) or
`None` (`network_latency`: every node). The engine wraps `notify` into the
event dict above. A cache outage with no cache sends nothing.

### 4. The plan, after the summary
Move the `if suggest:` block of `run()` into
`attach_fix_plan(self, summary: dict[str, Any]) -> dict[str, Any]` (mutates
and returns `summary`). `run(suggest=True)` calls it, so `run()` is
unchanged. Called before `run`, it raises `RuntimeError` whose message
contains "run".

### 5. `sim_core/feed.py` (pure: no SimPy, no `sim_core` import)
`Narrator().read(event) -> list[dict]` and `narrate(events) -> list[dict]`.
A line is `{"t", "kind", "severity", "node", "text"}`. `SATURATED_AT = 0.9`,
`RECOVERED_BELOW = 0.75`.

| kind | severity | when | text |
|---|---|---|---|
| `incident_start` | crit | chaos `start` | `component failure on db: 50% of its capacity is gone` · `network latency spike: every node is 1.5x slower` · `cache outage on redis: 80% of its hit rate is gone` |
| `incident_end` | info | chaos `end` | `component failure on db ended` · `network latency spike ended` · `cache outage on redis ended` |
| `saturated` | warn | a node's utilization reaches 0.9 and it is not already flagged | `db at 97%` |
| `recovered` | info | a flagged node drops below 0.75 | `db back to 62%` |
| `retries` | warn | a node's `retries` > 0 in the tick | `3 retries on db` / `1 retry on db` |
| `failures` | crit | the tick's `failed` > 0 (`node` is None) | `2 requests failed` / `1 request failed` |

Inside one tick: saturated/recovered in the tick's node order, then retries
in node order, then failures. Between 0.75 and 0.9 nothing is said. An event
type it does not know returns `[]`. Each `Narrator` has its own state.

## Result

### What changed
- `sim_core/engine.py` — `CloudSimulator(config, event_sink=None)` (`EventSink` alias). The sampler forwards each tick to the sink as `{"type": "tick", **tick}`; `_chaos_notifier` builds the chaos event dict, and is `None` (nothing built) without a sink. `_walk` calls `collector.record_edge(i)` right before it recurses; edges are indexed by identity (`id(edge)`), since the live graph walks the config's own `Edge` objects, so two edges between the same pair of nodes still count apart. The plan block of `run()` moved into `attach_fix_plan(summary)`; `run(suggest=True)` calls it, and calling it before `run` raises `RuntimeError("attach_fix_plan needs the run first: ...")`.
- `sim_core/metrics.py` — `MetricsCollector(..., edge_count=0)`; `record_arrival` counts; `record_edge`; `sample_utilization` builds, stores and returns (a deep copy of) the tick; `timeseries()` returns deep copies of the stored ticks. `UtilizationSample` / `collector.utilization` unchanged.
- `sim_core/chaos.py` — `Notify` alias; `inject(..., notify=None)` and each handler call `notify("start" | "end", node)` right after apply / release. The file's old style findings (`Optional`, `typing.Callable`) were fixed with `ruff --fix` so the card's ruff check passes.
- `sim_core/feed.py` — new: `Narrator`, `narrate`, `SATURATED_AT`, `RECOVERED_BELOW`, the table of the card.
- `sim_core/__init__.py` — exports `Narrator`, `narrate`.
- `docs/AGENTS.md` — the engine, metrics and chaos rows; a new `feed.py` row.
