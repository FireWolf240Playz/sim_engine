# Task 3.1b — `POST /runs` and the event stream

> Roadmap 3.1, second of three cards. Needs card 3.1 (`event_sink`, `attach_fix_plan`, `sim_core/feed.py`).

## Goal
A run is started with `POST /runs` and watched with
`GET /runs/{run_id}/events`: ticks, chaos windows and feed lines, then the
summary as soon as the simulation is done, then the full `/simulate` body
once the plan is verified.

## Measured first (2026-11-15)
A throwaway implementation of this card, over real HTTP (uvicorn), on
`microservice_platform` under `db_failover`: `POST /runs` answered in 0.13 s,
first tick at 0.28 s, `measured` at **0.7 s**, one `ping` at 15.7 s, `result`
at **27.2 s**. 60 ticks, 12 chaos events, 54 feed lines. Today the caller
waits the full 27 s for the first byte.

## Decided, and why
- **No new dependency.** The roadmap allows `sse-starlette`; a
  `StreamingResponse` with `media_type="text/event-stream"` over a plain
  generator does the same in 15 lines and is what the tests ran against.
- **`measured` before `result`.** The verdict does not wait for the plan
  (see the numbers above). `result` stays byte-equal to `/simulate`'s body,
  so a client can swap one call for the other.
- **A multi-seed run streams one run's ticks: the typical one.** Every seed
  is measured first (0.1 s each, a `seed` event apiece), the typical seed is
  picked, its recorded events are sent, then `measured`, then the plans.
- **The run keeps its events.** A reader that arrives late, reads twice, or
  reconnects with `Last-Event-ID` gets what it missed. This store becomes
  the `runs` table in Wave 4.
- **`/simulate` does not change.**

## Design (decided)

### Routes
- `POST /runs` — body `RunRequest` `{config, playbook?, n_seeds?, seeds?}`
  (the same meaning and limits as on `/simulate`; give the two models a
  shared base). Validate **before** starting, exactly as `/simulate` does
  (`apply_playbook_or_404`, `_resolve_seed_list`, `check_budget`): 404, 400
  and 422 come back from the POST with the same words. Then `store.create()`;
  `None` → 429 with a sentence containing "busy". Submit the worker, answer
  **202** `{"run_id", "events_url": "/runs/<id>/events"}`. `run_id` is
  `secrets.token_urlsafe(16)`.
- `GET /runs/{run_id}` → `{"run_id", "status": "running"|"done"|"failed", "result": {...}|null, "error": str|null}`.
- `GET /runs/{run_id}/events` → the stream. Headers `Cache-Control: no-cache`, `X-Accel-Buffering: no`.
- Unknown id on either GET → 404 `unknown run: 'nope'`.

### The stream
Each stored event is `id: <n>\nevent: <name>\ndata: <json>\n\n`, `n` counting
from 0 per run. `Last-Event-ID: n` resumes at `n + 1` (a value that is not
an integer is ignored). The stream ends after `result` or `error`.

| event | data | when |
|---|---|---|
| `started` | `{run_id, seed, seeds, duration, metrics_interval, chaos}` (`seeds` null for one run; `chaos` is the effective schedule, playbook included) | first |
| `seed` | `{seed, index, of, resilience_score}` | multi-seed only, one per seed, before any tick |
| `tick` | the engine tick, without `type` | per sample |
| `chaos` | the engine chaos event, without `type` | as it happens |
| `feed` | one narrator line | directly after the engine event that caused it |
| `measured` | `{summary, typical_seed}` — the summary **before** the plan | after the last tick |
| `result` | exactly what `/simulate` returns for this request with `include_timeseries=true` | last |
| `error` | `{"detail": "the run failed: <exception text>"}` | last, instead of `result` |
| `ping` | `{}`, **no id**, not stored | whenever nothing was sent for `HEARTBEAT_SECONDS` (15) |

### The worker (one thread per run, `ThreadPoolExecutor(max_workers=2)` on `app.state`)
Single run:
1. `narrator = Narrator()`; the sink publishes each engine event, then each line `narrator.read(event)` returns, as `feed`.
2. Build `CloudSimulator(config, event_sink=sink)`, publish `started` (with `simulator.seed`).
3. `summary = simulator.run(suggest=False)` → publish `measured`.
4. `simulator.attach_fix_plan(summary)` → build the `/simulate` body → `run.finish(body)`.

Multi-seed: publish `started`; for each seed run with a sink that only
appends to a list, publish `seed`; `typical = typical_index(summaries)`;
replay the typical run's recorded events through one `Narrator`; publish
`measured` (`typical_seed` set); `attach_fix_plan` on every run; build the
multi-seed body; `finish`. (The prototype confirmed the typical seed is the
same before and after the plan: the plan does not move the resilience score.)

Any exception → `run.fail(f"the run failed: {exc}")`. The worker never leaves a run open.

Three details the tests depend on:
- **Serialise at publish time.** `attach_fix_plan` mutates the summary
  `measured` was sent with; store the JSON text, not the dict.
- **Build the `result` body the way the route does**
  (`SimulateResponse(**body).model_dump(mode="json", exclude_unset=True)`,
  or the shared helper), so it equals `/simulate`'s response key for key,
  `report_png_b64: null` included.
- **The generator reads `api.runs.HEARTBEAT_SECONDS` each time it waits**
  (the test shortens it). Keep the generator in `api/runs.py`; do not
  `from api.runs import HEARTBEAT_SECONDS` into another module.

### `api/runs.py`
- `Run`: `run_id`, `status`, `result`, `error`; `publish(name, data)`,
  `finish(result)` (publishes `result`, status `done`), `fail(detail)`
  (publishes `error`, status `failed`); readers wait on a
  `threading.Condition` with a timeout (the heartbeat). The stream is a
  plain (sync) generator; Starlette iterates it in its thread pool.
- `RunStore(max_runs=MAX_RUNS, ttl_seconds=RUN_TTL_SECONDS, clock=time.monotonic)`:
  `create() -> Run | None`, `get(run_id) -> Run | None`. A finished run
  expires `ttl_seconds` after it finished; a running run never expires. At
  capacity, `create` drops the oldest finished run, or returns `None` when
  every run is still running. Defaults: 64 runs, 900 s.
- `create_app()` puts a fresh `RunStore` on `app.state.runs` (the tests replace it).

## Result

### What changed
- `api/runs.py` — new: `Run` (status, result, error, numbered events stored as JSON text at publish time, a `threading.Condition` for readers), `RunStore` (`create` / `get`, TTL on finished runs only, drops the oldest finished run when full, `None` when every run is running), `sse(run, last_seen)` (numbered events, an id-less `ping` after `HEARTBEAT_SECONDS` of silence, drains then ends after `result` / `error`). `HEARTBEAT_SECONDS` 15, `MAX_RUNS` 64, `RUN_TTL_SECONDS` 900. JSON is written with `allow_nan=False`, as `/simulate`'s response is.
- `api/routes/runs.py` — new: `POST /runs` (202), `GET /runs/{id}`, `GET /runs/{id}/events`; the worker `execute_run` (single and multi-seed, as the card's Design says) always closes the run.
- `api/routes/simulate.py` — `seed_config`, `single_run_body`, `multi_seed_body` take the response assembly out of the route; `/simulate`'s behaviour is unchanged. New signatures use `list[...]` / `X | None`.
- `api/schemas.py` — `RunSpec` (config, playbook, n_seeds, seeds) is the base of `SimulateRequest` and the new `RunRequest`; `RunStartedResponse`, `RunStatusResponse`.
- `api/main.py` — `app.state.runs` (a fresh `RunStore` per app), `app.state.run_pool` (`ThreadPoolExecutor`, `RUN_WORKERS = 2`), the router.
- `docs/AGENTS.md` — the `api/` section.
