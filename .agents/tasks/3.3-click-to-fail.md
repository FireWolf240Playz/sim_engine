# Task 3.3 — click-to-fail: "inject failure here"

> Roadmap 3.3. Needs 3.1 (ticks carry live `capacity`), 3.1b (`/runs`) and
> 3.1c (the web runs through the stream). Best after 3.2, where the failure is visible as it strikes.

## Goal
From the node inspector the user fails a node of their choice: a full outage
for 15 seconds, a third of the way into the run, on top of whatever incident
is selected. The run, the live view and an export all carry it.

## Measured first (2026-11-15)
- **The engine needs nothing.** `ChaosEvent.target` exists, and the config
  validator already refuses an unknown node. What is missing is a request
  field, one merge every route uses, and a refusal that reads as a sentence:
  the validator's own 422 is a list of Pydantic error objects.
- A full outage works: at `intensity: 1.0` the tick shows `capacity: 0` in
  the window and the configured size before and after (worker → db stack, and
  `order-service` on the 20-node example).
- On the small test stack the outage raises P95 from 5.46 s to 6.14 s and
  fails nothing (1 rps against a 10 s budget); the test pins that, not a score drop.

## Decided, and why
- **`custom_chaos` rides on the request, apart from `config`.** The config is
  the architecture; an injected failure is what is done to it, like the
  playbook. Putting it in `config.chaos` would make "the architecture" change
  every time the user clicks a node, and Fix-it and the change log compare architectures.
- **One failure per node, at most 8** (the API's limit).

## Design (decided)

### API
`effective_config(config, playbook, custom_chaos) -> SimulationConfig`:
1. `apply_playbook_or_404(config, playbook)` (404 / 400 as today).
2. No custom events → return that config **as is** (the same object when there is no playbook either).
3. Otherwise rebuild the config with `chaos = [*config.chaos, *custom_chaos]`
   **through validation** (`SimulationConfig.model_validate(...)`;
   `model_copy(update=...)` does not validate). Order: the config's own
   events, the playbook's, then the custom ones.
4. A `ValidationError` → `HTTPException(422, detail=<one sentence>)`: join
   the errors' `msg`, without Pydantic's `Value error, ` prefix. For an
   unknown node that is the validator's own
   `chaos event targets unknown component 'nope' (known nodes: [...])`.

A malformed event (intensity 2.0, an unknown field) is FastAPI's own 422, as
for any body. `/simulate` without `custom_chaos` answers exactly as before.

### `lib/clickToFail.ts`
- `failureEvent(node, config)` → `component_failure`, `intensity: 1`,
  `start_time = round(duration / 3)`, `duration = min(15, config.duration - start)`,
  `interval = config.duration` (so the next strike falls after the run: it happens once).
- `failureLabel(event)` → `db fails at 20s for 15s`.
- `withFailure(list, event)` (replaces the node's earlier failure, keeps at
  most `MAX_INJECTED = 8`, dropping the oldest), `withoutFailure(list, node)`,
  `failedNodes(list)`. None mutates its input.

### Web behaviour
- Node inspector: an `Inject failure here` button under the node's
  measurements. It calls `injectFailure(node)`, which adds the event and
  **starts a run** (the roadmap: "→ run"), then closes the inspector. When
  the node already has one: `Remove the injected failure` instead (no run).
- Incident bar: one chip per injected failure, text `failureLabel(event)`,
  with a remove button (`aria-label="Remove the failure on db"`). Removing
  does not run; the next Run goes without it.
- The failures persist across runs until removed, and are cleared when the
  architecture is replaced or reset. "Apply & re-run" keeps them (the fix is
  tested under the same failure).
- The diagram's incident targets include the failed nodes (accent ring before the run; the live view strikes them during it).
- The verdict's context line: `under db failover + 1 injected failure` / `with 1 injected failure` on a clean run.
- Every run sends `custom_chaos` (omit it when empty). `measuredRun.customChaos`
  is what the run on screen carried; `exportRequest` sends that, never the current chips.

## Constraints
- Chaos mutates live state only: this adds events, no new injector.
- `/simulate`'s response shape and every existing test stay unchanged.
- Full type hints. No new dependency. Tokens for every colour.

## Out of scope
- Choosing the intensity, the start or the length in the UI; other event types; failing an edge.
